## Controller boundary

A local Node runner is the only code that reads `.env` or calls providers. Both teams receive the same versioned rulebook and simultaneous public snapshot. Observations include all 22 players, centimetre-rounded positions/velocities, ball, score, phase, recent events, owned active orders and a private 500-character notebook. They exclude opponent orders/notebooks and RNG state. A phase-specific instruction explains what can execute; it never selects a pass target, keeper position or tactical action.

The JSON schema fixes match, decision, tick and team identities with constants. Models choose their own orders, intent and memory. Zod validates shape and finite ranges; the engine validates ownership, duplicates and phase legality. `guard` already moves the keeper, so a separate move for the same player is a duplicate. The model schema requires loft explicitly and a minimum 1% movement pace. Engine fixtures can still use omitted loft and any positive pace.

A normal decision is due every 60 ticks, at a phase boundary, or after a possession change once at least 15 ticks have elapsed since the previous decision. Phase transitions can require an earlier boundary. Each pair is observed before either request starts. An accepted response remains locked while only the rejected team gets one repair with the identical observation and concise feedback. The runner advances no simulation during API waits. Both accepted batches then commit atomically. Exhausted repairs use explicitly recorded empty orders: existing actions continue until expiry, with no substitute tactic. Permanent provider failures stop the job. Unperformed restart delivery abandons the match.

## Limits and provenance

Default test cap: 10 boundaries, 40 total requests including repairs, 4,096 output tokens per response, 32,768 input bytes, 600 wall seconds and $0.25 estimated cost. Before dispatch, reserve both requests and the entire repair allowance. Input-byte estimates include the rulebook, observation, schema and request overhead; use bytes as a conservative token estimate. Charge reported input/output usage when available, otherwise retain the full reservation. Cached input is conservatively charged at standard input rates. These are application estimates, not a guarantee about a provider's invoice. Request caps and API output-token caps are enforced separately. No SDK retries are hidden underneath this policy.

Only reviewed model configurations have prices. GPT-5 nano uses low reasoning and low verbosity. Its minimal-reasoning pilot repeatedly omitted kickoff delivery, despite valid transport. Low reasoning plus explicit phase instructions produced an accepted kickoff and open play. Gemini 2.5 Flash-Lite returned HTTP 404 explaining it was unavailable to new users on this account. We deliberately switched to available Gemini 3.1 Flash-Lite, minimal thinking, temperature 0.4. There is no automatic model upgrade.

Rates checked 2026-09-07: GPT-5 nano $0.05 input / $0.40 output per million tokens ([OpenAI model page](https://developers.openai.com/api/docs/models/gpt-5-nano)); Gemini 3.1 Flash-Lite $0.25 input / $1.50 output ([Google pricing](https://ai.google.dev/gemini-api/docs/pricing)). Output accounting includes reasoning/thinking tokens. Adapter fields follow [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [Gemini generateContent](https://ai.google.dev/api/generate-content) and the [Gemini model guide](https://ai.google.dev/gemini-api/docs/models/gemini-3.1-flash-lite). The Zod discriminated-union schema emitted `oneOf`, which OpenAI rejected; a union emits supported `anyOf` instead.

Record exact configurations, resolved model IDs, request IDs, latency, usage, validation errors, retry feedback, model response text, accepted actions, notebooks, observations and the shared prompt. The notebook/intent is model-authored text, not hidden reasoning. Published replay data contains no credentials. Checkpoint after committed boundaries; keep incomplete status when a cap, cancellation or provider problem stops generation. Preserve failed experiments privately rather than inventing their continuation.

## Replay and presentation

The entire viewport belongs to the broadcast. Decisions, observations, rules/prompt and recordings are behind one optional inspector. On desktop it sits alongside the pitch; on phones it is an overlay. Inspection follows the playhead and never shows later decisions. The observation stream is the recorded sequence of exact inputs, updated during playback; API token arrival timing is not simulated or presented as live generation. Replays make zero inference calls.

Import validates the entire record shape and numeric values, roster identities, timelines, decision identities and observation bindings. Preserve property insertion order after validation because the engine's diagnostic hash is over JSON serialization. The publisher re-simulates before copying a compressed match into the viewer catalogue. Static files use gzip to keep full matches practical; Fetch automatically decodes HTTP `Content-Encoding: gzip`, whereas a raw `.gz` file needs `DecompressionStream`. The loader distinguishes those cases and bounds decompressed input at 80 MiB. This viewer supports current engine/record format only; archival engine migration is deferred.

Goal banners, huddles and hopping sprites are presentation only. For 1.8 seconds after a recorded goal, sample the last pre-goal frame and draw the five nearest scoring teammates converging around the scorer. Do not change the record, RNG, physics or model orders. Reduced motion removes gathering/hopping. Actual setup positions appear when delivery resumes.

Synthetic audio starts only after an explicit unmute gesture. Ambient crowd and effects pause/mute with playback. Effects use stable events crossed by the forward playhead; seeking resets the cursor without replaying old whistles/goals. Sound stays at its natural pitch at other playback speeds, and above 2× only major events sound. Voices are capped. No external audio assets or inference are involved.

Player-order inspection now adds a presentation-only selection ring and target line. Exact repair user messages use the same pure formatter as the adapters, so the displayed wording cannot drift from the request template. The optional Match tab distinguishes generation wall time, request counts and estimated usage from the playing clock.

Goal incidents are stamped inside a fixed simulation step; their updated score appears in the following frame. Goal banners, huddles and cheers wait for that completed step. This matters when a sample lands exactly on the incident tick: otherwise the banner could briefly accompany the old score. Halftime/full-time events already use their completed clock boundary.
